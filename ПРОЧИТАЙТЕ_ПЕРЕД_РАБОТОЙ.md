# Гайд по работе с GitHub для команды Unity (для новичков)

## 0. Важный момент про .gitignore, который у вас уже мог сломаться

Если ты сделал коммит **до** того, как добавил `.gitignore`, то файлы вроде `Library/`, `Temp/`, `obj/` могли попасть в репозиторий раньше, чем гитигнор начал их игнорировать. Гитигнор не удаляет уже закоммиченные файлы — он только не даёт добавлять новые.

**Проверить, не попал ли мусор в репозиторий:**
```
git ls-files | grep -E "Library/|Temp/|Obj/|Logs/"
```
Эта команда показывает список файлов, которые Git отслеживает, и фильтрует те, что лежат в папках Library/Temp/Obj/Logs.

Если команда что-то вывела — надо убрать это из репозитория (но оставить на диске):
```
git rm -r --cached Library Temp Obj Logs
git commit -m "Remove Unity generated folders from repo"
git push
```
- `git rm -r --cached` — убирает файлы/папки из-под контроля Git, но не трогает их на твоём компьютере (флаг `--cached` — ключевое отличие от обычного удаления).
- `git commit -m "..."` — сохраняет это изменение как новую версию проекта с комментарием.
- `git push` — отправляет коммит на GitHub.

## 1. Базовые понятия (коротко, чтобы все говорили на одном языке)

- **Репозиторий (repo)** — папка проекта, за изменениями которой следит Git.
- **Коммит (commit)** — «снимок» состояния проекта в конкретный момент, с описанием, что изменилось.
- **Ветка (branch)** — отдельная линия разработки. `main` — основная ветка, в которой должен лежать рабочий, стабильный проект.
- **Push** — отправить свои коммиты с компьютера на GitHub.
- **Pull** — забрать изменения с GitHub на свой компьютер.
- **Merge** — слияние двух веток в одну.
- **Pull Request (PR)** — запрос на GitHub «пожалуйста, добавьте мои изменения из моей ветки в основную», который остальные могут посмотреть и одобрить перед слиянием.
- **Конфликт (conflict)** — ситуация, когда два человека изменили один и тот же кусок файла по-разному, и Git не может сам решить, что оставить.

## 2. Как участнику команды подключиться к проекту первый раз

1. **Склонировать репозиторий** — скачать его к себе на компьютер:
   ```
   git clone https://github.com/ВАШ_АККАУНТ/название-репозитория.git
   ```
   Это создаёт папку с проектом и уже настроенной связью с GitHub.

2. **Открыть проект в Unity** не из папки, а через Unity Hub → Add → выбрать склонированную папку. Unity сам сгенерирует локальные папки `Library`, `Temp` и т.д. — их не нужно коммитить, `.gitignore` уже должен их скрывать.

3. Первая загрузка проекта в Unity может занять время (импорт ассетов) — это нормально.

## 3. Варианты воркфлоу — от простого к правильному


### Вариант B: Ветки (branches) + Pull Request — рекомендую для команды

Идея: `main` — это всегда рабочая, стабильная версия игры. Каждый человек работает в своей ветке и не трогает `main` напрямую.

**Шаг 1. Создать свою ветку под задачу**
```
git checkout -b feature/имя-фичи
```
- `checkout -b` — создаёт новую ветку и сразу переключается на неё.
- Пример названия: `feature/player-movement`, `feature/main-menu-ui`.

**Шаг 2. Работать и коммитить как обычно**
```
git add .
git commit -m "Добавил движение персонажа"
```

**Шаг 3. Отправить свою ветку на GitHub**
```
git push -u origin feature/имя-фичи
```
- `-u origin feature/имя-фичи` — говорит Git «эта локальная ветка теперь связана с такой же веткой на GitHub», после первого раза достаточно просто `git push`.

**Шаг 4. Создать Pull Request на GitHub**
На сайте GitHub появится кнопка "Compare & pull request". Нажимаешь, пишешь что сделано, и просишь кого-то из команды посмотреть код перед тем, как он попадёт в `main`.

**Шаг 5. После одобрения — merge через кнопку на GitHub** (Merge pull request). Это добавляет твои изменения в `main`.

**Шаг 6. Обновить свою локальную main-ветку**
```
git checkout main
git pull
```
- `checkout main` — переключение на ветку main.
- `pull` — подтягивает то, что только что смержилось, включая чужие изменения.

**Шаг 7. Удалить отработавшую ветку (по желанию, для порядка)**
```
git branch -d feature/имя-фичи
```

## 4. Как избежать конфликтов в Unity-файлах (это критично!)

Unity-сцены (`.unity`) и префабы (`.prefab`) — это текстовые YAML-файлы, но менять их вручную при конфликте почти нереально.

**Главные правила:**
1. **Один человек — одна сцена в моменте.** Договоритесь в чате команды, кто сейчас работает над `MainScene.unity`, чтобы двое не редактировали её одновременно.
2. Используйте **отдельные сцены для тестов** каждого разработчика, а потом переносите готовые объекты в общую сцену через префабы.
3. Разбивайте функционал на **префабы** — их проще объединять, чем целые сцены.
4. В Unity включите **текстовый формат сериализации**:
   `Edit → Project Settings → Editor → Asset Serialization → Force Text`
   Это делает файлы сцен и префабов читаемыми как текст, что немного облегчает слияние.
5. Перед тем как начать работу — всегда `git pull`, чтобы не работать со старой версией сцены.

Если конфликт всё же случился в сцене — обычно проще, чтобы один человек вручную пересобрал изменения заново, чем разбирать конфликт построчно.

## 5. Шпаргалка по командам

| Команда | Что делает |
|---|---|
| `git clone <url>` | Скачать репозиторий первый раз |
| `git pull` | Забрать свежие изменения с GitHub |
| `git status` | Показать, какие файлы изменены |
| `git add .` | Подготовить все изменения к коммиту |
| `git commit -m "текст"` | Сохранить снимок изменений с описанием |
| `git push` | Отправить коммиты на GitHub |
| `git checkout -b имя` | Создать и перейти в новую ветку |
| `git checkout main` | Переключиться на ветку main |
| `git branch` | Посмотреть список веток |
| `git log --oneline` | Посмотреть историю коммитов кратко |

---

## 6. Рекомендация для вашей команды новичков

Раз вы только начинаете:
 Обязательно проверьте пункт 0 про `.gitignore` — сделайте это в первую очередь, пока в репозитории мало файлов.
